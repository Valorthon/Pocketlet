# 0002. PostgreSQL + Drizzle over JSON file storage

Status: Accepted
Date: 2026-08-25 (recorded retrospectively 2026-09-17)

## Context

Users, PIN hashes, and recovery state lived in `apps/web/.data/users.json`, read and rewritten on every mutation. This was fine for a single-process local demo and failed as soon as the app was deployed (issue #24):

- Railway containers have ephemeral filesystems — a redeploy discarded every account.
- Concurrent writes to one JSON file race and lose data.
- Claimable links needed relational queries (by `claim_hash`, by sender, by expiry) that a flat file cannot serve.

## Decision

PostgreSQL with [Drizzle ORM](https://orm.drizzle.team/), schema in `apps/web/src/lib/db/schema.ts`, migrations generated by `drizzle-kit` into `apps/web/drizzle/`. `apps/web/scripts/import-users-json.ts` was written as a one-off backfill.

Drizzle was chosen over Prisma mainly for its lighter runtime and a schema defined in plain TypeScript, which keeps types flowing without a generate step for every edit.

## Consequences

Data survives redeploys, concurrent writes are safe, and features like claim links and device keys become tractable. Local development now requires Postgres — hence `docker-compose.yml`, and hence the test suite needing a live database.

It also added a deployment concern: migrations must run before the new code serves traffic, which [0005](./0005-migrate-on-boot.md) addresses.

The migration was done quickly and **no foreign keys were defined**. `user_devices.email`, `claim_links.sender_email`, and `notifications.claim_link_id` had no referential integrity, which left orphan rows possible and made test cleanup incomplete. This was an oversight rather than a decision, and it was corrected in issue #62 — see [production-readiness.md](../production-readiness.md).

Note also that `stellar_address` was carried over from the classic-account era and duplicates `wallet_contract_id`.

## Alternatives considered

**SQLite on a persistent volume** — simpler, but Railway's volume story is awkward and it would not survive a move to multiple instances.

**A hosted document store** — no relational queries, and no real advantage over Postgres for this shape of data.
